PASOS REALIZADOS PARA MODIFICAR EL JMX
--------------------------------------
1. Abrir el script P2.jmx original con JMeter (modo GUI):
     ~/apache-jmeter-5.6.3/bin/jmeter -t P2.jmx
2. En el Thread Group, ajustar Number of Threads a [N] y Loop Count a [M].
3. Botón derecho sobre Thread Group > Add > Config Element > Counter.
   Configurar como arriba.
4. [Si CSV] Botón derecho > Add > Config Element > CSV Data Set Config.
   Crear el fichero candidatos.csv en el mismo directorio que el JMX.
5. En el HTTP Request del POST, sustituir los valores fijos por las variables
   ${idMesa}, ${candidato}, ${importe}, etc.
6. Guardar el JMX como P2.jmx (sobreescribiendo o el nombre que pida).

[SI EL EXAMEN PIDE 2.2 — investigar discrepancia]
-------------------------------------------------
Si el COUNT(*) es MENOR que el esperado pero JMeter reporta 0% de errores,
las acciones a realizar dentro de JMeter son:

1. Añadir un "View Results Tree" como listener al Test Plan, y lanzar 5-10
   iteraciones en GUI. Inspeccionar la pestaña "Response data" de cada POST
   para ver si la respuesta HTML es la de "pago/voto incorrecto" en lugar
   de la de éxito (status HTTP 200 pero contenido de error).

2. Añadir un "Response Assertion" sobre el POST de pago/voto, comprobando
   que el body contiene "[texto de éxito esperado]". Eso convertiría los
   200 silenciosos en errores explícitos en el resumen de JMeter.

3. Añadir un "Aggregate Report" para comparar throughput vs filas en BD.

4. Comprobar que el Counter está bien configurado (Per User: false) y que
   no estamos enviando combinaciones (idComercio, idTransaccion) duplicadas
   que el constraint UNIQUE de la BD rechaza.

5. Comprobar la Cookie Manager: si "Clear Cookies each Iteration" está mal
   marcado, todas las iteraciones de un mismo hilo van al mismo backend
   (sticky session). En cluster, esto no es problema; en single VM, no
   tiene efecto, pero si afecta al CSRF token sí.
